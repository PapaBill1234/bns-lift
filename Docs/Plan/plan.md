# bns-lift plan

## Goal

Lift the 2019 + PDB server executables to C++ source that compiles again. Then change the packets to the 381 client and add the missing parts.

| Phase | Output | Check |
| --- | --- | --- |
| 1. Lift | C++ source for each exe, built with clang-cl | The exe builds. The exe starts under Wine. |
| 2. Verify | Packet logs of the original exe and the lifted exe | The two logs are the same for the same input. |
| 3. Port to 381 | Packet structs and handlers for the 381 client | The 381 client gets the same packets as from the 381 server. |
| 4. Add | Functions that are in 381 but not in 2019 + PDB | A packet log from the 381 server set is covered. |
| 5. Modernise | Clean code, tests, then optional Rust | Phase 2 and 3 checks still pass. |

## Rules

- This repo is PRIVATE. The code comes from NCSoft binaries. Never push it to a public repo (slopemulator).
- Do not put binaries in git: no `.exe`, `.dll`, `.pdb`, `.i64`, `.lib`, `.obj` or data files.
- Never write keys, passwords or certificates. Write `keyhere`.
- Use names from the PDB only. Do not invent names. If a name is not in the PDB, use the IDA name and mark it `// ❓`.
- Phase 1 is a mechanical lift. Keep the original logic, including bugs. Mark each bug with `// BUG:` and one line. Phase 5 fixes the bugs.

## Toolchain (verified 2026-11-15)

```
clang-cl (LLVM 21) ──► .obj ──► lld-link ──► .exe ──► wine64
   │                              │
   ├─ Wine C headers               ├─ Wine import libs (libmsvcr100.a, libmsvcp100.a, libkernel32.a, ...)
   │  /usr/include/wine/wine/msvcrt└─ own crt0 (mainCRTStartup)
   └─ Wine Windows headers
      /usr/include/wine/wine/windows
```

| Item | Value |
| --- | --- |
| Compile flags | `/GS- /X -imsvc <wine>/msvcrt -imsvc <wine>/windows /D_WIN64 /D_MSVCR_VER=100` |
| Link | `lld-link /nodefaultlib /entry:mainCRTStartup` + Wine `.a` import libs in `/usr/lib/x86_64-linux-gnu/wine/x86_64-windows/` |
| C++ STL | Not in Wine. Write our own subset in `include/vs2010/` with the VS2010 object layout (from the PDB types). |
| Do not use | mingw (other C++ ABI), xwin (needs a Microsoft licence acceptance), `-fms-compatibility-version=16` (removes `char16_t`, Wine headers fail) |
| Test | `hello.exe` with a virtual class: output `lift ok 2 32` under Wine. |

## Lift method (one PDB module per step)

1. Open the IDA work copy. Read the module function list (`tools/` or IDA `execute_python`).
2. Decompile each function with Hex-Rays.
3. Write clean C++ with the PDB types and names. Remove casts and temporaries that Hex-Rays adds. Keep the logic.
4. Put inlined STL code back as STL calls (`std::vector::push_back`, not the raw buffer code).
5. Build with `tools/gate.sh`. Fix all errors.
6. Write the handoff: modules done, functions done, open items with addresses.

## Verify method (phase 2)

- Tools: `bns-wine/pktlog/` (`pktlog.dll`, `patch_import.py`, `pkldump.py`, `pktcover.py`).
- Give the same input to the original 2019 + PDB exe and to the lifted exe. Compare the packet logs.
- The Wine server set (`bns-wine/`) is the 381 set. A 2019 + PDB exe can have a different protocol to its peers. If it does, write a replay harness: it sends a captured stream to the exe and records the replies.

## Orchestrator

- The runner makes the worktree from this repo, runs `tools/gate.sh`, merges into `main` and pushes to the private GitHub repo.
- Rules for lift sessions: `bns-server/tools/slices/lift-rules.md`.

## Planner chain

The queue makes new cards by itself. You do not write cards for servers 2 to 13 by hand.

```
lift-cg-5 ─► lift-smartcoupondaemon-plan ─► lift-smartcoupondaemon-1..N ─► lift-lobbygate-plan ─► ...
                         │                              └─► lift-smartcoupondaemon-verify
                         └─ writes cards + Docs/Plan/queue/<id>.tsv
```

1. A planner card `lift-<slug>-plan` reads the PDB of its server. It skips the modules that are already in `src/common/`.
2. It writes the lift cards, the verify card and the next planner card (from `Docs/Plan/planner-template.md`).
3. It writes the queue rows to `Docs/Plan/queue/lift-<slug>-plan.tsv`.
4. After the gate passes, the runner (`chain_lift` in `slice_runner.py`) adds the valid rows to `queue.tsv`. Valid = 9 columns, kind `lift`, id starts with `lift-`, id not in the queue, paths not empty.
5. The next planner depends on the last lift card of the server, not on verify. A failed verify does not stop the chain.
